= Architecture and State Map Guide
:toc:
:sectnums:

== Purpose

A topology page is a concise map of a project's actual architecture, intended
boundaries, and known gaps. It complements implementation docs; it is not a
completion score, CRG assessment, compliance certificate, or substitute for
build/test evidence.

== Required content

. *Current components*: name the real crates, services, packages, or modules;
  link their source and describe what each currently does.
. *Boundaries*: distinguish implemented paths from planned paths. Label a
  conceptual diagram as a target whenever it is not wired end to end.
. *Dependencies and ownership*: show which component depends on which contract
  and who owns each boundary. Identify runtime dependencies separately from
  development and governance tooling.
. *Evidence and limits*: cite test/build/proof surfaces and state the exact
  scope they support. A configured workflow is not a passing workflow run.
. *Update protocol*: specify which implementation or observed evidence change
  justifies an update.

== Honest status vocabulary

Use one of these labels and include paths or run links where relevant:

[cols="1,3", options="header"]
|===
| Label | Meaning

| Implemented
| Source exists and its stated behaviour has a corresponding test or other
  direct evidence. State the boundary of that evidence.

| Experimental
| A working component exists, but its API, adoption, supported targets, or
  operational context remains narrow or unvalidated.

| Planned
| Accepted direction with no implementation claim.

| Blocked
| A named dependency, decision, toolchain, or test prevents the next step.

| Unassessed
| No adequate evidence has been collected. Do not convert this to a failing or
  passing grade without a formal assessment.
|===

Do not use completion percentages, progress bars, aggregate grades, or badges
unless a project has defined a repeatable measurement and can publish its
source evidence. Never infer a certification from using a template, workflow,
or policy set.

== Agent prompt for a project topology page

[source,text]
----
Inspect the repository and update its architecture/state map using only evidence
in the current checkout. Name the real components and their source locations;
separate implemented dataflow from conceptual/future flow; describe ownership,
contracts, and hard dependency boundaries; cite actual test/build/proof gates
and their limitations. Mark missing or unverified evidence as planned, blocked,
or unassessed. Do not invent completion percentages, grades, badges, passing
workflow results, integrations, or runtime dependencies. Keep RSR/estate
governance separate from product runtime architecture. If two projects are
intended to interoperate, specify a versioned, independently implementable
contract and preserve the ability to use either project without adopting the
other. Make the smallest coherent edit and report claims that could not be
verified.
----

== Relationship to machine-readable estate files

A project may use `.machine_readable/` for structured state and governance. A
human-readable topology should agree with those files, but it does not replace
them and must not upgrade a policy declaration into evidence that a gate passed.
