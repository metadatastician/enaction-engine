= Enaction Engine Roadmap
:toc:

This roadmap is evidence-gated. Implementation now exists in parts of Phases 1,
2, 5, and the cross-cutting coprocessor boundary, but no phase has real-game
adoption from this repository. Later phases are intended direction, not release
commitments or claims of complete subsystems. A component earns its way in
through a real game, working code, tests, and a stable boundary.

== Admission rule

Before a roadmap item becomes an implemented engine component it needs:

* a concrete proving-ground use or unavoidable substrate requirement;
* an implementation with proportionate tests;
* provenance and known limits;
* a host-neutral boundary tested against game-specific assumptions;
* no speculative empty crate.

== Phases

=== 1. Deterministic time and replay substrate — active

Implemented now: fixed-timestep stepping, whole-step support, render-only
interpolation, double buffering, discontinuity handling, and tests.

Next committed work is integration evidence: exercise `enaction-time` in a game
host, preserve replay inputs independently of presentation, and measure shortcut
behaviour under stalls. Full replay storage is not implemented here yet.

=== 2. World-state and event substrate — partial, unadopted

`enaction-trace` implements typed, ordered and caused events, trope identity,
belief kinetics, theory-of-mind ascription paths, retraction, and a perspective
belief store. `enaction-contracts` implements versioned CAC/ESM types and
package validators. A general world/state substrate, snapshots, persistence and
game adoption remain absent.

=== 3. Host and rendering boundary — exploratory

Define reusable frame-host contracts, completed-state views, discontinuities,
and presentation sampling. A renderer is not implied by the current buffer.

=== 4. Agency and action — exploratory

Represent embodied agents, affordances, constraints, chosen actions, and
consequences over host-defined entities and events.

=== 5. Cognitive state — partial seam, unadopted

Belief, salience/interest kinetics, false-belief ascription, retraction and
projection queries are implemented and tested. Perception, attention, general
memory, inference and planning are not complete subsystems. No game consumes
the seam, so its generality remains provisional.

=== 6. Affective state — typed boundary only

The trace can distinguish affective events and carries unsigned salience, but
valence, appraisal, mood, atmosphere, trust, fear and attachment are not
implemented. A domain tag is not an affect subsystem.

=== 7. Conative state — exploratory

Develop needs, motives, goals, commitment, inhibition, and action selection,
with explicit relationships to cognition, affect, and available action.
The domain vocabulary exists, but goal, commitment and behavioural-selection
machinery does not. ADR-0017 forbids creating it before real-game service and a
recorded boundary surprise.

=== 8. Networking and persistence — exploratory

Build from deterministic state, ordered events, snapshots, replay, protocol
versioning, and recovery evidence. Multiplayer claims require real multi-peer
tests.

=== 9. Asset and presentation systems — exploratory

Admit assets, rendering, animation, sound, music, and input through tested host
boundaries. Do not couple simulation correctness to a presentation backend.

=== 10. UMS integration — exploratory

Implement a versioned game profile, compiled package format, headless
validation, and optional Enaction preview adapter without a runtime/editor
cycle.

=== 11. Extraction from IDApTIK — active proving-ground programme

Inventory candidate seams, integrate `enaction-time`, and extract only
facilities whose boundaries survive removal of IDApTIK-specific rules. Record
whether each component is copied, generalised, or new.

=== 12. Validation against Chronicles of Slavia — planned abstraction test

Use a second game's materially different ontology and demands to challenge the
host, world, agency, and content contracts. Refactor boundaries that only fit
IDApTIK rather than papering over them with game-specific engine concepts.

== Interface constraints

* A BEAM numeric or byte-buffer adapter uses `hyperpolymath/snifs`: a
  freestanding WebAssembly guest, Zig `ReleaseSafe`, explicit fallibility,
  bounded execution, and no silent fallback. Operations needing the wider
  `erl_nif` surface require a separate ADR.
* A Zig FFI must pass the estate Hexadeca purity floor: no direct `std.fs` or
  `std.io` in the FFI. Passing that floor does not manufacture a sixteen-
  connector protocol API. A unified Hexadeca connector is admitted only when
  a real protocol-facing consumer needs it.
* The stable interface chain is Idris2 ABI authority to deterministic generated
  declarations to Zig FFI to host bindings. Rust code additionally requires
  Creusot contracts and a fail-closed verification gate before formal Rust
  correctness is claimed.

== Commitment boundary

Committed repository work is recovery and validation of the implemented
crates, truthful proof accounting, and proving-ground integration when
scheduled by the games. Unimplemented portions of Phases 2–10 and Phase 12 are
exploratory direction until backed by an accepted scoped proposal and
implementation work. The 2026-11-30 naming review is a governance deadline,
not a feature-delivery promise; evidence, not calendar optics, advances an
implementation phase.
