= Enaction Engine Architecture Topology
:toc:

This page describes the repository that exists today. It is an experimental
library workspace, not a complete game engine or an RSR template service.
Component boundaries are real; the end-to-end runtime flow below is a target,
not an integration claim.

== Current components

[cols="1,2,3", options="header"]
|===
| Component | Location | Responsibility and boundary

| Deterministic time
| `crates/enaction-time/`
| Fixed-step accounting, double buffering, and render-only interpolation.
  No game loop or host is included.

| Typed trace
| `crates/enaction-trace/`
| Game-neutral causal events and cognitive/affective/conative state queries.
  It does not select an agent's behaviour.

| Package contracts
| `crates/enaction-contracts/`
| Version and validation primitives. This is not a full content package
  protocol or a dependency on the UMS application.

| CPU accelerator reference
| `crates/enaction-accelerator/`
| Operation planning and deterministic scalar kernels.

| Native accelerator boundary
| `src/interface/Abi/`, `src/interface/generated/abi/`,
  `src/interface/ffi/`, `crates/enaction-accelerator-native/`
| Idris2 ABI authority, generated declarations, Zig implementation, and Rust
  adapter. ABI v1 currently requires 64-bit pointers; model-to-compiler
  correspondence is tested, not fully proved.
|===

== Conceptual runtime flow

[source,text]
----
Game host (not implemented)
        |
        v
whole fixed steps ----> host-owned world and systems ----> render interpolation
        |                         |
        |                         +----> typed trace (optional seam; not adopted)
        |
        +----> contract-validated content packages (future consumer seam)
        |
        +----> capability plan -> CPU reference or optional Zig-native adapter
----

The diagram records intended integration seams; the workspace does not yet wire
them into one application. Renderer, entity/component model, input, physics,
audio, networking, persistence, and a runnable host remain future work.

== Product boundaries

* Games own their domain ontology, host loop, and game-specific rules.
* Enaction Engine must remain independently usable; it must not depend on the
  Universal Modding Studio application. Any future UMS exchange belongs at a
  versioned data/contract boundary that a game can also produce or consume on
  its own.
* `.machine_readable/`, GitHub workflows, and `build/just/` provide repository
  governance and verification. They support development; they are not runtime
  engine subsystems or certification evidence.
